# 공통 커밋 규칙

이 문서는 앞으로 팀이 사용할 커밋 양식입니다. 실제 Stage 범위와 순서는 해당 작업의 커밋 계획을 따릅니다. 최초 이관용 일회성 가이드는 현재 문서가 아닙니다. AI의 실행 권한과 보존 원칙은 [작업 규칙](../ai_docs/WORKING_RULES.md)을 따릅니다.

## Commit subject

```text
[접두어] 실제 변경 요약
```

대괄호와 접두어 다음에 공백 한 칸을 넣고, 한 줄로 핵심 변경을 씁니다. `Commit subject :`라는 글자는 실제 제목에 넣지 않습니다. 접두어는 아래의 대소문자를 유지합니다. ‘수정’, ‘작업’만 쓰기보다 바뀐 대상과 결과가 드러나게 씁니다.

```text
[Fix] 삭제된 샘플 씬 기본 경로 제거
[Docs] 팀 작업 문서와 커밋 안내 정리
[Art] 프라이팬 스프라이트와 장착 위치 적용
```

## 접두어 목록

[Feat]

새 게임 기능이나 도구 기능 추가입니다. 예: 등록 맵의 직전 맵 제외 순환.

[Fix]

기존 동작의 오류 수정입니다. 예: P2 조준 표시의 로컬 슬롯 연결 수정.

[Art]

이미지·모델·폰트·효과음과 해당 임포트·연결 변경입니다. 효과음 코드 버그처럼 핵심이 코드 수정이면 Fix를 사용합니다.

[UI]

화면 배치·표시·전환·애니메이션 변경입니다. 아트 파일 추가가 주목적이면 Art, 기능 오류 해결이 주목적이면 Fix를 선택합니다.

[Map]

맵 정의·배치·테마와 등록 목록 변경입니다. 맵 제작 도구의 새 기능은 Feat, 도구 오류는 Fix로 구분합니다.

[Refactor]

기능·규칙을 유지하는 코드 구조 개선입니다. 판정이나 밸런스 변경을 숨기는 접두어로 사용하지 않습니다.

[Test]

자동 테스트·검증 시나리오·기준 자료의 추가와 수정입니다. 기존 실패를 감추기 위해 기대값을 바꾸지 않습니다.

[Docs]

사용법·설계·작업 기록 등 문서 변경입니다.

[Chore]

초기 프로젝트 추가, Git 제외 규칙, 빌드·개발 환경 설정 등 유지관리 작업입니다.

하나의 커밋에는 주목적에 맞는 접두어 하나를 씁니다. 이번 첫 이관처럼 기존 게임 전체를 추가할 때는 Chore를 사용하고, 이후부터 기능별 커밋으로 나눕니다.

## Description

Description은 제목 아래의 본문입니다. 변경 이유·실제 변경·중요 파일·실제 검증·남은 영향을 짧게 적습니다. 아래 항목은 내용이 있을 때 채우고 불필요한 빈 항목은 생략합니다.

```text
변경 목적
- 어떤 문제나 작업을 위한 커밋인지

주요 변경
- 실제로 달라진 동작이나 추가한 자료

중요 파일
- 경로: 파일의 역할 또는 검토할 변경

검증
- 실제 실행한 확인과 결과
- 실행하지 않은 검사는 미실행으로 표시

영향 및 주의
- 씬·입력·온라인·리플레이·맵·에셋 참조 영향
- 남은 문제나 팀원이 알아야 할 사항
```

## Stage 범위

코드는 같은 기능의 씬·프리팹·설정·에셋과 함께 묶습니다. Unity 에셋은 대응하는 `.meta`도 포함하고, 이름 변경은 이전 경로 삭제와 새 경로 추가를 함께 확인합니다.

서로 독립된 문서 문단이나 코드 수정은 부분 스테이징할 수 있습니다. 씬·프리팹·`.meta` 일부나 서로 의존하는 기능을 임의로 떼지 않습니다. 선택한 파일만으로 실행되는지 확인하지 않았다면 보장하지 않습니다.

라이선스 고지는 해당 외부 자료와 함께 넣습니다. Library·Temp·개인 로그·빌드·녹화·LocalOnly·민감정보는 포함하지 않습니다. 실제 제외 범위는 `.gitignore`와 권리 안내를 따릅니다.
