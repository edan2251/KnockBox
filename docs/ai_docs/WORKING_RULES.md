# 현재 작업 규칙

이 문서는 팀과 AI가 함께 따르는 장기 작업 원칙입니다. **최신 사용자 지시가 이 문서보다 우선합니다.**

현재 승인 범위와 진행 상태는 [PROGRESS의 현재 승인 범위](progress/PROGRESS.md#현재-승인-범위)에만 적습니다. 이 문서에는 승인 기록을 누적하지 않습니다. Unity Play의 직접 검수는 사용자가 맡습니다. 과거 요청서·명세·로그에 적힌 자동 진행·삭제·커밋 지시는 당시 기록입니다. 그 기록만으로 현재 작업 권한이 늘어나지는 않습니다.

## 작업 위치와 Git

작업 경로를 먼저 확인합니다.

- 원본 프로젝트: `D:/BrawlGame/Project_Brawl`
- 새 작업 위치: `D:/KnockBox`
- 새 저장소: `edan2251/KnockBox`

원본 프로젝트의 미커밋·미추적·Git 제외 자료, 백업, 실험 자료는 보존합니다. 이관은 최신 작업 파일을 선별해 복사하는 방식입니다. 원본 `.git`과 커밋 이력은 새 저장소에 가져오지 않습니다.

이관 당시 기존 **3개 커밋과 README**를 유지했고, 현재는 사용자의 첫 게임 커밋 `0b3cb54`가 추가되어 있습니다. 기존 이력을 변경하지 않습니다. 이관 확인 당시 새 저장소는 `main`, 원본 개발 브랜치는 `exp/brawl-v1`였습니다. 원본의 브랜치 규칙을 새 저장소에 그대로 적용하지 않습니다. 브랜치를 임의로 만들거나 전환하지도 않습니다.

**스테이징·커밋·푸시는 사용자가 Fork에서 직접 합니다.** 원격 설정, 공개 범위, Git 이력은 변경하지 않습니다. 기능 브랜치 운영과 공동 작업 방식은 팀 안내의 권장안이며, 별도 합의 전에는 강제 규칙이 아닙니다.

## 보존과 공유

기존 내용을 임의로 덮어쓰거나 삭제·대량 이동하지 않습니다. 이관 전에는 원본과 분리된 백업을 만들고 다음을 확인합니다.

1. 보존할 파일의 목록·크기·해시
2. 별도 위치에서 실제로 복원할 수 있는지
3. 새 위치에 이미 있는 파일과 충돌하는지

백업이 실패하거나 자료를 잃을 위험이 있으면 **전체 작업을 멈추고 보고합니다.** 기존 파일은 조사 후 합의한 범위에서만 보완합니다. README는 그대로 유지하고, `.gitignore`는 프로젝트에 필요한 제외 규칙을 검토해 보완합니다.

공개 저장소에 넣을 자료는 별도로 확인합니다.

- `LocalOnly`, 외부 참고자료, 개인 녹화·캡처·로그·빌드를 무심코 포함하지 않습니다.
- 공유가 불확실한 자료는 [권리 확인](../licenses/ASSET_RIGHTS.md)과 [이관 기록](HISTORY.md)에 남깁니다.
- 원본에 남긴 자료가 모두 Git으로 복구된다고 가정하지 않습니다.
- 비밀값·인증 토큰·참가 코드는 문서나 콘솔 출력에 남기지 않습니다.

Unity Cloud 연결·권한·과금 설정은 바꾸지 않습니다. 새 패키지·에셋 설치와 계정 변경도 별도 승인 없이 진행하지 않습니다.

## 프로젝트 동작과 편집

Unity 버전은 `ProjectSettings/ProjectVersion.txt`를 기준으로 합니다. 이관 기준 버전은 **6000.3.23f1**입니다. 임의로 올리거나 내리지 않으며, 기존 manifest와 lock 파일의 의존성을 보존합니다.

팀의 주 작업 씬은 Main과 MapAuthoring입니다. Sandbox는 검증·문제 재현용으로 유지합니다. 편집한 실제 씬 오브젝트·프리팹이 실행에도 사용되어야 합니다. 초기화 도구로 편집된 Main을 다시 생성하지 않습니다.

편집 위치, 설정값, 맵 저장, 파일 이름 기준은 [팀 작업 안내](../team/TEAM_WORKFLOW.md)를 따릅니다. 생성하는 GameObject의 내부 이름은 영문·숫자·밑줄만 사용합니다. 공백이나 구분자는 _로 바꿉니다. 버튼·설명·게임 표시 문구는 별개이며 한글을 유지합니다. 이름 변경 전에 문자열 경로 참조를 확인하고, 고유 ID·.meta·외부 원본 파일을 이 규칙 때문에 일괄 변경하지 않습니다.

기능을 만들거나 수정하기 전에 기존 구현·호출 경로·적용 설정·관련 검사를 먼저 확인합니다. 기존 코드를 수정하거나 재사용할 수 있는지 판단한 뒤 필요한 부분만 추가합니다. 관련 문제를 발견하면 재현 근거를 확인하고 승인 범위에서 함께 수정합니다.

새 파일·클래스·관리자·인터페이스를 추가할 때는 맡을 책임과 기존 코드로 해결하지 않은 이유를 보고에 한 줄로 적습니다.

과거 동작을 위한 호환 분기는 보존할 맵·기록·리플레이가 있거나 사용자가 요구할 때 둡니다. 중간 시도를 호환 분기 없이 교체하는 것은 그런 맵·기록·리플레이와 사용자 요구가 없음을 확인했을 때만 합니다. 이미 있는 호환 분기는 별도 승인 없이 지우지 않습니다.

게임을 수정할 때는 다음 동작을 보존합니다.

- 전투 규칙과 입력의 의미
- 틱과 랜덤 소비 순서
- 기존 온라인 결정론과 리플레이 호환성

경기 판정을 Unity 물리로 대체하지 않습니다. 자세한 계층 규칙은 [현행 개발 명세](CURRENT_DEV_SPEC.md), 온라인과 공통 코드의 경계는 [온라인 코드 지도](ONLINE_CODE_MAP.md)를 봅니다.

이관 승인에는 대규모 코드 재배치, asmdef 변경, 새 게임 규칙·밸런스 확정, 이전 캐릭터 실험 삭제가 포함되지 않았습니다. 예상하지 못한 판정·호환성 변화가 생기고 해결하지 못했다면 해당 변경을 중단하고 근거를 남깁니다.

## 검증과 보고

Unity를 제어하기 전에 실제 대상 프로젝트 경로를 확인합니다. 특히 MCP가 원본과 새 프로젝트 중 어디에 연결되었는지 추측하지 않습니다.

**에디터가 열려 있는 같은 프로젝트를 별도 배치 모드로 실행하지 않습니다.** 씬을 전환하기 전에는 미저장 편집을 확인하고, 사용자 작업을 덮어쓰지 않습니다.

검증은 변경의 영향 범위에 맞춰 진행합니다. 실행할 검사는 [변경별 검사](../team/TEAM_WORKFLOW.md#변경별-검사)에서 고릅니다. 문서·주석만 바꾼 경우 Unity 전체 검사를 반복하지 않습니다.

1. 기존 실패와 새 실패를 구분해야 하면 변경 전에 같은 관련 검사를 실행합니다.
2. 변경 후 컴파일과 고른 검사를 실행합니다. 화면·경기 흐름이나 맵 편집 흐름이 바뀌었다면 사용자 확인 절차도 남깁니다.
3. 코드가 바뀌면 관련 명세·주석·사용 안내가 실제 동작과 맞는지 확인합니다.
4. 실제로 실행한 검사와 결과, 실패, 실행하지 못한 검사를 구분해 보고합니다.

과거 리플레이의 기대 체크섬과 기준값을 새 결과로 덮어쓰지 않습니다. 통과시키려고 검사 기준을 약화하지도 않습니다. 의도한 동작 변경이면 사용자 승인 후 같은 변경에서 기대값과 기록을 함께 고칩니다. CI와 Git 훅은 없으므로 검사가 자동으로 실행된다고 보고하지 않습니다.

친구와의 두 PC Relay 실기는 현재 보류입니다. 자동 검사나 로컬 실행만으로 실제 온라인 실기를 완료했다고 하지 않습니다. 불필요한 반복 검사·스크린샷·영상은 만들지 않습니다.

보고에는 **실제 수행·통과한 것 / 제안 / 미확인**을 나누어 적습니다. 이관 당시 결과는 [외부 보관 기록](HISTORY.md), 현재 상태는 [PROGRESS](progress/PROGRESS.md)를 확인합니다. 이 규칙 문서 자체는 완료 선언이 아닙니다.

승인된 범위는 묶어서 진행하고 결과를 보고합니다. 백업 실패, 자료 유실 위험, 예상 밖 기존 파일 충돌처럼 중요한 문제는 중단하고 설명합니다. 범위를 넘는 삭제·설치·권한 변경을 작은 구현 선택으로 처리하지 않습니다.
